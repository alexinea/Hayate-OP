# HayateOP 2.6 — O1 lean fast path benchmark report (2026-09-10)

> Purpose: verify the **O1 acceptance criterion** for the 2.6 performance batch — the opt-in lean
> (wrapper-free) fast path must bring single-operation latency *and* allocation onto the level of
> `Microsoft.Extensions.ObjectPool` (MEOP), the zero-wrapper reference implementation, instead of the
> ~15x gap the general-purpose engine showed in the 2.5 baseline.

## 1. What was measured

The benchmark matrix (`tests/HayateOP.Benchmarks`) covers the full `Acquire` / `Release` /
`AcquireAsync` paths and is split into three BenchmarkDotNet categories: `reference`, `hot` and
`concurrent`. This report is built from **one `--anyCategories reference hot` run**, so the MEOP and
plain-`new` reference rows were measured in the same process, on the same warmed machine state, as
the Hayate rows — every number below is directly comparable.

| Implementation | Configuration |
| :--- | :--- |
| `Microsoft.Extensions.ObjectPool` | `DefaultObjectPool<PooledObject>`, `MaximumRetained = MaxPoolSize` (reference baseline) |
| plain `new` | no pool at all — the allocation lower bound |
| HayateOP AllOff | general engine, every optional feature disabled |
| **HayateOP Lean** | **`WithLean()` — the O1 wrapper-free fast path** |
| HayateOP Sharded4 | general engine, sharding only (4 shards) |
| HayateOP Full | general engine, every feature enabled |

All pools are pre-warmed during `GlobalSetup` (borrow `MaxPoolSize` objects, then return them), so
the steady state never reaches the creation path; `MinPoolSize = 250`, `MaxPoolSize = 300`.

## 4. Key conclusions

1. **Parity with MEOP on the single-threaded round trip.** `Acquire+Release | Hayate Lean` is
   **27.063 ns** against MEOP's **26.950 ns** — 0.4% apart, i.e. inside one standard deviation of
   either measurement (2.09 ns / 1.01 ns), and BenchmarkDotNet's own normalized ratio for the lean
   row is **1.01**. The 2.5 baseline measured the general engine at 251.8 ns / 384 B, roughly 15x
   MEOP; the lean path closes that gap completely.
2. **Zero allocation.** The lean path allocates **0 B** per synchronous `Acquire+Release` round trip —
   the same `B/Op` picture as MEOP. The 384 B credited to the general engine is the
   `HayateObject<T>` wrapper plus its free-list node; removing it was the second half of the O1 goal.
   Only the asynchronous path allocates (144 B), and that is the `async` state machine, not the pool.
3. **~10.6x faster than the general-purpose engine with everything off** (27.1 ns vs 286.8 ns). That
   is the concrete payoff of dropping the wrapper allocation, the per-shard free-list spin lock, the
   registry lookup on return and the diagnostic writes from the borrow/return path.
4. **Release is symmetric**: `Release | Hayate Lean` 30.5 ns against `Release | MEOP Return` 26.2 ns
   (1.16x), and 10.5x faster than `Release | Hayate AllOff` (320.2 ns).
5. **The general engine keeps its own cost ladder** — AllOff 286.8 ns, Sharded4 285.9 ns,
   Full 415.0 ns — which is expected: those configurations pay for the per-object state that
   validation, eviction, leak detection and metrics are built on. Lean mode deliberately normalizes
   all of them away, so it is a mode selection, not a tuning knob.
6. **100-thread contention** (separate run, `2026-09-10-o1-lean-concurrent.csv`): Hayate Lean
   20.87 us / 4034 B against MEOP 25.74 us / 4065 B, and against the general engine's 142.8 us
   (Sharded4) / 144.2 us (AllOff). This suite shows run-to-run variance far above the CI thresholds
   and is therefore recorded but **never gated** — see the baseline's `excluded` flag.

## 5. Variance, resolution limits and caveats

The two sub-50 ns rows sit at the resolution limit of this hardware, and this machine is a
laptop-class CPU: repeated measurements of the *same* benchmark move by up to 2.4x across runs. The
honest reading of the head-to-head is therefore the ratio, not the absolute figure.

Three additional isolated runs — `HayateOP.Benchmarks.exe --filter '*Meop_AcquireRelease*'
'*Hayate_Lean_AcquireRelease*'`, i.e. only the two small benchmarks and nothing else in the process —
are archived as `2026-09-10-o1-lean-isolated-repeats.csv` (merged, with an added leading `Run`
column identifying the repeat):

| Run | `Acquire+Release \| Hayate Lean` | `Acquire+Release \| MEOP` | Lean / MEOP |
| :--- | ---: | ---: | ---: |
| isolated 1 | 59.18 ns | 46.75 ns | 1.27 |
| isolated 2 | 30.49 ns | 25.05 ns | 1.22 |
| isolated 3 | 31.95 ns | 19.45 ns | 1.64 |
| combined run (this report) | 27.06 ns | 26.95 ns | 1.00 |

So the lean path tracks MEOP within a factor of **1.0-1.6x** depending on run conditions, with the
combined run reporting parity. What *is* stable across every run is the allocation column: the lean
path is a reproducible **0 B** per synchronous round trip.

Two further caveats:

* The general-purpose engine's rows move by roughly +/-13% between runs, which is larger than any
  change introduced by O1 (see the isolated-runs table for the same effect on MEOP). The committed
  baseline is therefore marked `calibration: true` and its numbers are advisory.
* The `Allocated` column for the general engine is not stable across runs (0-1065 B for the same
  benchmark) because the first measured iterations amortise lazily created internal structures over
  the operation count. Do not read those cells as steady-state allocation rates.

## 6. Benchmark description rename (breaks comparison against 2.5)

The 2.6 work renamed the benchmark descriptions, and the rename is significant when comparing
against the 2.5 reports (`2026-09-10-m1-bdn-baseline.md`, `2026-09-09-t11-benchmark.csv`):

| 2.5 description | 2.6 description | Meaning |
| :--- | :--- | :--- |
| `Hayate Lean` | `Hayate AllOff` | general-purpose engine with every optional feature off |
| — | `Hayate Lean` | the new opt-in wrapper-free fast path (`HayatePoolOptions.EnableLean`) |

Anything comparing against the 2.5 numbers must read `Hayate AllOff` where the older reports read
`Hayate Lean`.

## 7. Reproduction

```bash
# full matrix (reference + hot + concurrent)
dotnet run -c Release --project tests/HayateOP.Benchmarks -- --anyCategories reference hot concurrent

# the single-threaded head-to-head only
dotnet run -c Release --project tests/HayateOP.Benchmarks -- --anyCategories reference hot

# regression gate against the committed baseline
python scripts/bench-compare.py BenchmarkDotNet.Artifacts/results/HayateOpBenchmarks-report.csv
```

Artifacts land in `BenchmarkDotNet.Artifacts/results/` (CSV is the machine-readable form consumed by
`scripts/bench-compare.py`; the `github.md` export is the Markdown table quoted above).
